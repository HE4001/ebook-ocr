### 2.1 主代理与子代理的职责

本节落实用户新增要求，优先于本文和详细规格中未区分执行者的编码、测试安排。

**主代理负责：**

- 明确需求、完成条件、接口和文件归属，将任务交给编码子代理。
- 阅读当前代码、差异和子代理报告，作静态审查及必要运行验收。
- 明确决定接受或退回；退回时提供文件、问题、原因、具体修改要求和验收点。
- 协调共享文件、依赖及整合顺序，维护计划、进度、审查记录和最终报告。
- 统一执行必要测试、构建、PDF 编译及界面验收，保存真实证据。

主代理不得自行编写或修补业务代码、基础设施实现、接口接线、样式、迁移或测试实现；发现问题后交回对应子代理处理。跨模块接线和冲突修复也是编码任务，交由有明确文件归属的子代理完成，不能以“集成”为由由主代理代写。主代理可编辑需求、计划、审查及验收文档。

**所有子代理必须遵守：**

1. 模型为 gpt-6.1-sol，推理强度为 xhigh。先阅读分配范围并思考方案，然后直接编码和静态自查。
2. 不得进行任何测试或运行验证，包括单元/集成/端到端测试、冒烟、构建、类型检查、lint、试编译 LaTeX、运行应用、启动服务、接口探测、数据库迁移试跑、浏览器验收和性能测试。
3. 不得以“快速检查”“导入确认”“小脚本”或“验证一下”为名运行修改后的代码，也不得触发带测试或运行钩子的工具绕过限制。
4. 所有编码子代理不得进行 computer use：不使用 CUA、浏览器自动化、浏览器或桌面 UI 操作、截图式 UI 检查，也不通过其他代理或工具间接执行。
5. 可以读取文件、搜索代码、查看静态差异、编辑分配文件。静态自查不等于测试，不可在报告中宣称功能已验证。
6. 不过度设计，不进行防御性编程。只实现明确需求所需逻辑，不引入假设性分支、重复校验、静默兜底、广泛异常吞噬、多层通用包装、预留插件框架或额外兼容层。
7. 保留规格已经明确要求的数据边界、结构校验、人工编辑保护及编译执行约束；这些是本任务的具体功能，不以“避免防御性编程”为由删除。已在入口校验的内部值不重复层层防御。
8. 追求代码简洁、职责直接、命名清楚和可维护性，优先复用现有模块，不为未来假设增加抽象。
9. 只改分配文件，不覆盖用户或其他子代理的改动；发现越界需求先向主代理报告接口和所需文件，由主代理协调归属。
10. 不再自行分派下级代理；并行调度统一由主代理负责。交付明确声明“未进行任何测试或运行验证，未使用 computer use”。

“不得测试”限制所有子代理的执行行为；必要测试和复现代码如属于明确分配的交付，由相应编码子代理编写后交给主代理运行，不由子代理执行。默认不为低影响改动新增测试框架或成套测试。

### 2.3 并行顺序与模型设置

1. 主代理先读取当前状态并给出最小接口要求，M1 首先实现公共契约。主代理静态审查并接受契约后，冻结本轮字段、函数签名和错误/质量状态。
2. 在契约明确后，并行派发 M2、M3、M4。三者可以独立编码，但不能靠猜测接口建立临时兼容分支；接口变更由主代理协调 M1。
3. 有并发名额且相关接口可用时启动 M5。没有名额时排队或复用已经结束的模块代理，不创建额外聊天。
4. 主代理逐模块审查并决定接受或退回。模块接受后由 M5 或相应文件所有者进行必要集成编码；再由主代理执行相关运行验证。
5. 运行验证产生问题时分配给对应模块修改，所有返工仍遵循禁止测试和 computer use 的要求。

并发数量以运行时槽位为准。当前会话最多 4 个活跃代理含主代理，因此最多同时运行 3 个子代理；无需为了五个模块同时运行而绕过限制。

使用 collaboration 子代理工具，不使用创建用户聊天的 create_thread。创建时显式设置 model 为 gpt-6.1-sol、reasoning_effort 为 xhigh；当前工具要求模型覆写时使用 fork_turns 为 none 或有限历史，建议 none 并传递完整任务及必要上下文。不传 all 后依赖模型继承。模型不可用时报告具体障碍，不静默换模型或推理强度。

### 2.5 审查、退回与接受

主代理检查每份交付的实际差异，不能只根据子代理自述接受。至少审查：需求覆盖、原行/公式保真、数据及源码权威、接口一致性、文件越界、状态竞争、用户改动保护，以及是否存在不必要抽象、重复分支、兜底或防御性编程。

审查结论只有两类：

- 接受：说明接受的范围和理由；未运行验证时必须注明“仅代码审查接受，待主代理验证”，不能直接标工作包 verified。
- 退回：列出文件/函数、具体缺陷、为何不接受、期望修改及重新审查条件。交回原模块子代理，主代理不直接修补。

返工后重新查看差异，检查问题是否修复以及是否引入其他问题。接口争议由主代理决定单一约定，再将修改要求交给相应文件所有者。

每次决定记录到执行进度的审查表。子代理结束仅表示交付实现；主代理接受且必要验证通过后，相关工作包才能进入 verified。

## 4. 执行范围

### 4.1 可以自主推进

以下是整个 Goal 的任务范围，不代表子代理可以执行全部动作：编码交给 M1—M5；测试、构建、编译、服务启动、运行验证和界面操作仅由主代理执行。主代理不参与基础编码，第 2 节的角色约束始终适用。

- 修改仓库中相关后端、前端、测试、依赖声明和文档。
- 复用本地 Python、Node、pnpm、XeLaTeX 和 PDF 工具进行测试及编译。
- 只读检查原图、PDF 和相关页面结果，将必要书稿字段复制到隔离目录，不复制凭据表。
- 在 .cache/rendering-repair/ 创建复现、参考标注、临时数据、PDF、截图和日志。
- 启动独立端口的隔离服务验证界面；先检查端口和进程，不停止已有 OCR 作业。
- 根据证据调整内部实现，并记录原因；完成标准和数据保护要求保持不变。

### 4.2 本目标不包含

- 用已保存密钥发起真实付费识别、批量重新识别整书、自动切换模型或供应商。
- 在用户原库上试迁移、覆盖人工书稿、批量删除来源文件及旧缓存。
- 上传书籍、数据库或凭据；对外部署、发布或推送远端。
- 新增多用户、EPUB、自动图像重绘、通用工作流引擎或阅读器产品。

这些是本 Goal 的范围，不要求每次编辑、测试、编译重新请示。工具权限或依赖不足时先使用可用本地替代；确实缺少授权的动作按当时工具规则处理。

| 免费验证 | 固定响应、合成夹具、原图校准和实际编译 | 不宣称已验证真实上游质量 |
| 参考标注 | 执行者查看原图，在隔离夹具中校准 | 不把丢失断行的旧源码当正确基线 |
| 源码编辑 | 自由源码保存后显式脱离旧布局 | 不允许两套正文互相覆盖 |
| 优先级 | 裁切、分页、漏报先于美化 | 不扩展无关界面功能 |

内部类型名和模块划分可自主调整。若改用前端 PDF 渲染库，先验证依赖和交互收益。

在小样本上核准规格第 11.2 节的标注方法和容差，再冻结到进度文件。不能为通过失败样本而放宽指标；发现指标定义不合理时，记录原值、证据及替代方法，实质降低目标需用户决定。

## 7. 执行循环与跨轮恢复

每个工作单元由主代理按以下分工推进：

1. 从进度表选择依赖具备、优先级最高的未完成项。
2. 主代理根据代码、自己取得的失败证据或视觉差异明确需求、接口及验收点。
3. 交给文件归属模块的 gpt-6.1-sol / xhigh 子代理思考后编码、静态自查，禁止测试和 computer use。
4. 主代理审查实际差异；不接受则提出具体修改意见交回子代理，接受后由主代理运行必要测试、编译或 UI 检查并记录证据。
5. 运行不通过则由主代理定位和提出修改要求，子代理返工；主代理不得直接修补，也不得无变化重复命令等待通过。
6. 通过后主代理更新审查决定、状态、证据和下一步，继续后续工作，不逐阶段等待“继续”。

恢复时先读当前包、未解决失败、下一步并核对实际代码。只有代码、工具或证据变化使检查失效时才重跑，不重复稳定通过的完整套件。

工作包状态：pending、in_progress、implemented、verified、blocked。implemented 只表示代码已写，不能计入 Goal 完成；工作包 blocked 不等于 Goal 工具 blocked。

## 8. 验证执行要求

本节所有命令和运行操作只交给主代理。所有子代理禁测；不能把验证拆给一个“测试子代理”来规避要求。主代理可作代码审查、运行验收和文档记录，但测试或复现实现本身仍须交给明确归属的编码子代理静态编写。

### 8.1 隔离环境

优先复用 .venv、现有前端依赖和 XeLaTeX。数据库测试用临时路径或 EBOOK_OCR_DATA_DIR 指向隔离目录；先检查应用导入是否初始化数据库，避免误写原库。

已有服务运行时不直接调用 Restart/Stop 脚本。界面验证使用独立前后端端口及对应地址，确保没有连接回用户原实例。

### 8.2 命令与实际验证

以下是执行入口，不是已通过记录。每个包先跑定向测试，整体验收再覆盖必要套件。

PowerShell 从仓库根目录运行：

~~~powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
~~~

在 frontend 目录运行：

~~~powershell
pnpm test
pnpm run build
~~~

先核实运行时及当前脚本。缺少依赖、版本不适配或历史断言失败时查明原因，修复本次范围内问题，不能改成跳过来制造通过。

原有无关失败必须记录基线、影响和未被本次加剧的证据；必要验收及受影响链路仍须通过。无法判断是否相关时作为未解决问题。

PDF 必须通过应用自身导出链路实际生成。渲染全部 11 页，与原图逐页查看并记录原行、公式组、裁切、基线及分页；不能只看前三页就签全批通过。

实际 UI 至少验证：同页对照、问题定位、窄窗口、未保存草稿、保存后重编、编排变化、快速切页后旧请求返回、旧模板与完整文档。构建通过不能代替交互验证。

### 8.3 证据位置

~~~text
.cache/rendering-repair/
  baseline/          原输出、基线结果及原有失败
  reference/         校准参考、原行、坐标及指标
  runs/<run-id>/     PDF、诊断、页映射、渲染图、命令日志
  isolated-data/     隔离数据及必要书稿资源，不含真实凭据
docs/
  RENDERING_REPAIR_PROGRESS.md
  RENDERING_REPAIR_VERIFICATION.md
~~~

验收报告由执行阶段根据真实结果创建，不预先生成通过记录。敏感附件保存在已忽略的 .cache 中，提交用夹具使用原创合成内容。报告须写明方法和结论，不能只有本机路径。

## 9. 障碍处理与目标状态

- 代码错误、编译错误和待修复测试不是立即停止理由。
- 缺工具先查现有环境及替代路径；真实模型调用未获授权，不妨碍固定响应、排版和 UI 验证。
- 原样本缺失时继续通用实现及合成检查，但 G1—G3 的本地样本验收保持未完成，列明缺少页及恢复办法。
- 预算或系统限制到达时保存进度和下一步，不标完成、不自行增加预算。
- 只有用户明确要求暂停才设置暂停；局部障碍优先绕开推进独立工作。
- Goal 阻塞状态遵循实际工具规则。当前规则要求同一外部障碍至少连续三个 Goal 轮次仍阻止所有有意义进展，才可设为 blocked；三次重复命令不是三个轮次。恢复后重新核查。
- 阻塞报告列出具体障碍、尝试过的不同路径、证据、剩余门槛和解除障碍所需的最小输入。

## 10. 最终审计与交付

主代理完成前把 G1—G7 分别关联到代码、自己的验证结果及本地证据，运行 git diff --check 并核查变更范围。确认所有模块已经明确审查接受，没有回滚用户工作、覆盖原数据或将书稿及凭据加入待提交文件。发现编码缺陷仍交回子代理修正。

最终验收报告必须包含：

1. 变更摘要和 R01—R08 的实际处理状态。
2. W00—W11 结果及 G1—G7 逐项证据。
3. 11 页源页/输出页映射、视觉检查和关键误差。
4. 测试及构建命令、退出码、失败处理和现存无关问题。
5. 是否运行真实模型；未运行时明确固定响应的证明边界。
6. 新对照/校准流程、旧项目使用方式和回退步骤。
7. P2 及其他已知限制。
8. M1—M5 的子代理模型/推理强度、交付与审查结论、退回修改记录；区分子代理未测试与主代理实际验证，不能将子代理静态自查写成测试通过。

所有必要门槛满足后才将 Goal 标为 complete。预算目标完成时按工具要求报告返回的最终 token 用量；没有预算时不编造预算或用量。

最终答复简要说明完成结果、验证和报告位置。不要以“剩余工作可继续”结束一个仍可推进、必要条件尚未满足的目标。
